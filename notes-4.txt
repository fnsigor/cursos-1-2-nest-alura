a linha
```
providers: [AutenticacaoService],
```

por baixo dos panos é a mesma coisa que 

```
  providers: [
    {
      provide: AutenticacaoService,
      useClass: AutenticacaoService,
    },
  ],
```

"provide" é a classe que recebe Injectable() é declarada como dependencia em controllers e estaticos
"useClass" é a classe que de fato vai ser instanciada

observe o exemplo:

```
  providers: [
    {
      provide: AutenticacaoService,
      useClass: ClasseASerIntanciada,
    },
  ],
```

uma pipe pode declarar como depdencia a classe AutenticacaoService, mas quem de fato vai ser instanciada é a classe ClasseASerIntanciada

esse controle dos providers pode ser util em variso casos, como clsses fake pra usar mocks.









Token não baseado em classe:

tambem podemos substituir os token por strings ao inves de classes
```
  providers: [
    {
      provide: 'MEU_TOKEN',
      useValue: {
        login: () => {
          // código qualquer...
        },
      },
    },
  ],
```

dessa forma, a injeção de dependencia ficaria assim
```
@Controller('autenticacao')
export class AutenticacaoController {
  constructor(@Inject('MEU_TOKEN') private readonly autenticacaoService) {}

  // código omitido...
}
```

O valor em "provider" não é uma mera classe, e sim um token. As classes colocadas como valor nessa prop são tokens, e as classes que vão ser instanciadas são as da prop "useClass". Essa associação se chama registration.


podemos substituir classes que seriam injetadas por um valor literal, atraves da troca de useClass por useValue

Utilizar tokens de string em conjunto com o @Inject permite uma maior flexibilidade no uso de provedores, principalmente quando estamos lidando com libs já prontas. 
no controler de produto, usamos o token personalizado CACHE_MANAGER pra manipular o comportamento do redis

Além de strings, symbols do JavaScript e enums do TypeScript podem ser utilizados como tokens não baseados em classe.

Guards, em sua estrutura, são classes com um decorator @Injectable que implementam a interface CanActivate, esse método retorna um boolean indicando se determinada requisição é permitida ou não.

Ciclo de vida dos guards:
atuam depois da request ser feita pelo client e antes da request bater no controller

guards são semelhantes ao middlewares do express, mas atuam antes de chegar ao controller e sabem o que vai ser executado a seguir (executionContext)

Guards e casos de uso com Nest.js

- Autenticação:
Podemos verificar credenciais, tokens, chaves ou outra forma de autenticação suportada. Nesse contexto, um Guard irá atuar de fato como um Guardião da rota, pois irá protegê-la através da verificação das regras de autenticação.

- Autorização:
A lógica de autorização também pode ser aplicada por meio de um Guard. Após autenticar o usuário, um Guard pode verificar se ele carrega as permissões para realizar uma determinada operação ou acessar recursos da aplicação. Se o usuário não for autorizado a acessar uma rota de Administrador, por exemplo, um Guard pode negar o acesso e retornar um erro.

- Early exit (saída antecipada):
Guards podem interromper o processamento de uma requisição antes de alcançar o controlador. Essa ação é muito útil quando alguma condição não é atendida e, seja por questões de segurança ou regras de negócio, não precisamos continuar com o processamento da requisição. Nesse sentido, é possível permitir que um Guard retorne uma resposta ao cliente de forma direta, evitando assim adicionar processamento no controlador.

- Validação de dados:
Antes de uma requisição ser processada pelo controlador, Guards podem ser utilizados para validar os dados. Podemos incluir nesse contexto a verificação de parâmetros de URL, payloads, dados enviados no corpo da requisição, cabeçalhos, dentre outros. Caso os dados enviados não apresentarem os requisitos esperados, um Guard poderá rejeitar a requisição e enviar uma resposta de erro.

- Lógica de negócios:
Guards também são flexíveis para se adaptarem a regras de negócios. É possível executar lógica de negócios específica para uma rota de acordo com a necessidade. Assim, cada rota pode conter requisitos de validação e segurança distintos.

- Logging e métricas:
Podemos registrar informações relevantes sobre as requisições e respostas, a fim de capturar métricas ou para auxiliar no monitoramento e depuração da aplicação.
